# Стратегия защиты данных: Encryption at Rest & In Transit

| Данные                                                              | Необходимость защиты                                                                            | Инструменты защиты                                                                                                                                                                  |
| ------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **1. Персональные данные (PII)**<br>(ФИО, паспорт, СНИЛС, контакты) | - Соответствие 152-ФЗ<br>- Риск идентификации личности<br>- Высокая ценность для мошенников     | - **At Rest:** AES-256 (TDE в БД)<br>- **In Transit:** TLS 1.3 с PFS<br>- **Дополнительно:** Tokenization в логах                                                                   |
| **2. Медицинские записи (PHI)**<br>(диагнозы, анализы, назначения)  | - Врачебная тайна (ст. 13 ФЗ-323)<br>- Риск шантажа/дискриминации<br>- Высокие штрафы за утечку | - **At Rest:** Format-Preserving Encryption<br>- **In Transit:** Mutual TLS (mTLS)<br>- **Дополнительно:** Водяные знаки в PDF                                                      |
| **3. Финансовые транзакции**<br>(реквизиты карт, платежи)           | - PCI DSS compliance<br>- Риск финансового мошенничества                                        | - **At Rest:** HSMs (Thales PayShield)<br>- **In Transit:** TLS + дополнительное шифрование на уровне приложения<br>- **Дополнительно:** Маскирование в UI (первые/последние цифры) |
| **4. Учётные данные**<br>(логины, хэши паролей)                     | - Риск компрометации всей системы<br>- Атаки credential stuffing                                | - **At Rest:** Adaptive Encryption (scrypt + AES)<br>- **In Transit:** Только через VPN/IPSec<br>- **Дополнительно:** Hardware Security Modules                                     |
| **5. Метаданные операций**<br>(время визитов, специалисты)          | - Возможность деанонимизации<br>- Риск анализа поведения                                        | - **At Rest:** Deterministic Encryption<br>- **In Transit:** QUIC-протокол<br>- **Дополнительно:** Ограничение выборок (k-анонимность)                                              |
| **6. Системные логи**<br>(аудит действий)                           | - Риск утечки через логи<br>- Необходимость целостности                                         | - **At Rest:** Immutable Storage (WORM)<br>- **In Transit:** Sigv4 подпись запросов<br>- **Дополнительно:** Централизованное хранение логов с RBAC                                  |

## Классификация средств защиты

### Программные решения:

1. **Шифрование в rest**:

   - Базы данных: PostgreSQL pgcrypto, SQL Server Always Encrypted
   - Файлы: VeraCrypt для томов, Apache Tika для контент-анализа

2. **Шифрование in transit**:

   - API: Istio с автоматическим mTLS
   - Браузер: WebCrypto API для client-side шифрования

3. **Управление ключами**:
   - HashiCorp Vault + AWS KMS с авторотацией
   - OpenPGP для асинхронных сценариев

### Аппаратные решения:

1. **HSM**:

   - Для платежей: Thales PayShield 9000
   - Для инфраструктуры: AWS CloudHSM

2. **Сетевые устройства**:
   - Cisco ASA с поддержкой IPSec/IKEv2
   - Hardware Load Balancers с аппаратным TLS-терминированием (F5 BIG-IP)

## Автоматизированный контроль

1. **Системы мониторинга**:

   - Проверка незашифрованных данных: OpenDLP
   - Контроль конфигураций: Chef InSpec с CIS Benchmark

2. **Оркестрация**:

   - Автоматическая ротация ключей: через Kubernetes External Secrets
   - Политики шифрования: OPA/Gatekeeper

3. **Анализ рисков**:
   - Статический анализ: GitLeaks для поиска ключей в коде
   - Динамический анализ: Vault Fuzzer для тестирования API

## Критерии выбора инструментов:

1. Поддержка российских стандартов (ГОСТ Р 34.10-2012)
2. Возможность аппаратной изоляции (SGX, TrustZone)
3. Совместимость с существующей инфраструктурой 1С
